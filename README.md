# cleaner

CLI на Go для очистки combo-файлов в CSV-строки `"email","password"` / `"username","password"` в `C:/Source/combo`.

## Требования

- Go 1.22+
- Windows
- Каталог `C:/Source/combo` должен существовать

## Сборка

```bash
go build -o cleaner.exe ./cmd/cleaner
```

## Запуск

```bash
./cleaner.exe -save
./cleaner.exe -delete
./cleaner.exe
```

Флаги:

| Флаг | Значение |
|---|---|
| `-delete` | удалять исходники после успешной обработки (без prompt) |
| `-save` | оставлять исходники (без prompt) |

Если флаги не заданы — интерактивный вопрос:

```
Удалять исходные файлы после обработки? (1/delete = удалить, 2/save = оставить):
```

Ответы: `1` / `delete` или `2` / `save` (без учёта регистра). Оба флага сразу — ошибка (exit 2).

## Поведение

- ROOT жёстко: `C:/Source/combo` (нет `-root`)
- Обрабатываются только top-папки; файлы в корне `combo` игнорируются
- Уже обработанные top-папки читаются из `C:/Source/combo/cleaned.txt`
- Берутся `.txt` / `.csv` (регистр расширения не важен), имена с `_cleaned` и файл `readme.txt` пропускаются
- Входные записи: `LOGIN:PASS`, `URL:LOGIN:PASS` и `LOGIN:PASS:URL`; разделителями могут быть `:`, CSV, `|`, `;`, tab и прбелы, кавычки и экранированные `"` разбираются как CSV
- Перед обработкой каждый найденный `.txt`/`.csv` потоково проверяется тем же парсером до первой подходящей записи; файлы без единой валидной пары пропускаются без создания `_cleaned` и без удаления исходника
- Проверка не ограничена первыми N строками, поэтому mixed-файл с валидными данными после большого блока мусора не будет пропущен
- Поля короче 5 символов и явный мусор (имена/пути файлов, JSON, длинный Base64, email в пароле, hash/UUID/token-артефакты, значения в квадратных скобках — включая незакрытые, многочастные пути, короткие токены вида `число/токен`, `ключ=пакет/путь`, метки кодирования, шаблонные присваивания, профили приложений, домен в username, query-string и повторы) удаляются; обычный `@` в пароле разрешён
- Не-email username длиной от 40 символов и любой login длиной от 65 символов считаются metadata; также удаляются UUID внутри username, служебные `SocialLogin`-значения и дополнительные файловые расширения (`.req`, `.xlsm`, `.database` и аналоги)
- Email-подобный login удаляется и при любой длине, если до `@` в него склеен URL или путь (`domain/path/...user@email`)
- Строки длиннее 2 КиБ удаляются до извлечения пары, чтобы случайный хвост большого blob не превращался в валидную запись
- Значения пароля длиной от 30 символов удаляются, если они не соответствуют именованным форматам хэшей из Raccoon Parser или Argon2. Поддерживаются hex-дайджесты длиной 32/40/48/51/56/64/96/128, bcrypt, Argon2, PHPass (`$P$`/`$H$`), MD5/SHA crypt, MySQL5, Drupal, Django SHA, APR, `$HEX[...]`, `$SHA[...]` и варианты MD5 с солью после `:`. В варианте `MD5:соль` соль удаляется, остаётся чистый 32-символьный MD5; остальные форматы хэшей сохраняются целиком. Класс `unknown` из Raccoon Parser не считается подтверждённым хэшем; PBKDF2, yescrypt и scrypt crypt по этому правилу не сохраняются. У шаблона `MD5+8 символов_ДД.ММ.ГГГГ` хвост удаляется, остаётся чистый MD5
- Формат сам по себе не доказывает происхождение значения: например, 32 hex-символа могут быть как MD5/NTLM, так и идентификатором. Такие неоднозначные значения сохраняются согласно правилу сохранения известных форматов хэшей; нераспознаваемый хэш может быть удалён
- После этих проверок удаляются строки с `==@`, `android`, `discord`, `bot` (слова — без учёта регистра) или `//`. Если пароль распознан как хэш, эти фрагменты в пароле игнорируются, но в логине по-прежнему приводят к удалению
- Самым последним шагом пара преобразуется в CSV: `login:password` → `"login","password"`; внутренние `"` удваиваются
- Повторная обработка уже очищенной CSV-строки даёт тот же результат
- Результат: `{stem}_cleaned{ext}` рядом с исходником
- При 0 оставшихся строк исходник не удаляется
- Коды выхода: `0` ок, `1` ошибки файлов, `2` fatal
